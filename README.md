## 2. Тестлэгдэх систем

Лекц 5-ын жишээ систем — хичээлд бүртгүүлэх API. Сервер нь `server.js`
(цэвэр Node.js, нэмэлт сан шаардлагагүй, in-memory өгөгдөл) бөгөөд
`http://localhost:3000` дээр ажиллана.

```bash
node server.js
```

| Endpoint | Метод | Зориулалт | Хүсэлтийн бие (JSON) | Хариу |
|---|---|---|---|---|
| `/students/:id` | PUT | Оюутны бичлэг тавих (setup) | `{"status":"active","coursesTaken":["CS201"]}` | `200 {"result":"OK"}` |
| `/courses/:id` | PUT | Хичээлийн бичлэг тавих (setup) | `{"prerequisites":["CS201"]}` | `200 {"result":"OK"}` |
| `/courses/:id` | GET | Хичээлийг харах | — | `200 {"courseID","prerequisites"}` / `404` |
| `/registrations` | POST | **Тестлэгдэх функц** — хичээлд бүртгүүлэх | `{"studentID":"B231234567","courseID":"CS313"}` | Доорх хүснэгт |
| `/registrations` | GET | Бүртгэлүүдийг харах | — | `200 [{registrationID,studentID,courseID}]` |

### POST /registrations-ийн хариу

| Нөхцөл | Статус | Хариуны бие |
|---|---|---|
| Амжилттай бүртгэл | 201 | `{"result":"OK","registrationID":n}` |
| Оюутан байхгүй | 200 | `{"result":"ERROR_NO_STUDENT"}` |
| Оюутан идэвхгүй (status ≠ "active") | 200 | `{"result":"ERROR_INACTIVE_STUDENT"}` |
| Хичээл байхгүй | 200 | `{"result":"ERROR_NO_COURSE"}` |
| Урьдач нөхцөл дутуу | 200 | `{"result":"ERROR_PREREQUISITES","missing":["CS201"]}` |
| studentID эсвэл courseID талбар дутуу | 400 | `{"result":"ERROR_BAD_REQUEST"}` |
| Буруу JSON | 400 | `{"result":"ERROR_BAD_JSON"}` |

Сервер шалгалтыг дараах **дарааллаар** хийдэг (давхар алдааны хослолыг тайлбарлахад чухал):
`талбар бүрэн эсэх → оюутан байгаа эсэх → оюутан идэвхтэй эсэх → хичээл байгаа эсэх → урьдач нөхцөл`.

## 3. Тест дизайн — Лекц 5-ын 5 алхам

### Алхам 1 — Бие даан тестлэгдэх функц

`POST /registrations` — өөрөөр хэлбэл **хичээлд бүртгүүлэх** үйлдэл.
Оролт: `studentID`, `courseID`. Гаралт: статус код + `result` утга (+ `missing`, `registrationID`).

### Алхам 2 — Сонголт ба төлөөлөх утгын хүснэгт

| # | Сонголт (фактор) | Эквивалент анги (төлөөлөх утгууд) |
|---|---|---|
| **F1** | `studentID`-гийн хүчинтэй байдал | a) идэвхтэй оюутан (`status="active"`) · b) идэвхгүй оюутан (`status="inactive"`) · c) бүртгэлгүй оюутан |
| **F2** | Оюутны үзсэн хичээлүүд (`coursesTaken`) | a) урьдач нөхцөлийг бүрэн хангана · b) огт хангахгүй (хоосон эсвэл холбоогүй хичээл) · c) зарим нь хангана |
| **F3** | `courseID`-гийн хүчинтэй байдал | a) байгаа хичээл · b) байхгүй хичээл |
| **F4** | Хичээлийн урьдач нөхцөл (`prerequisites`) | a) урьдач нөхцөлгүй (хоосон массив) · b) бүгд үзсэн · c) огт үзээгүй · d) зарим нь үзсэн |
| **F5** | Хүсэлтийн биеийн бүрэн бүтэн байдал | a) `studentID` ба `courseID` хоёулаа байна · b) аль нэг талбар дутуу эсвэл хоосон мөр (`""`) |
| **F6** | Хүсэлтийн биеийн JSON хүчинтэй байдал | a) хүчинтэй JSON · b) эвдэрсэн (parse хийгдэхгүй) JSON |

### Алхам 3 — Спецификаци (13 спецификаци)

Лекцийн стратегиар: happy path **1**, алдааны анги бүрд **1** (нийт 4),
давхар алдааны сонирхолтой хослол **2**, хязгаарын тохиолдол **5**, зарим урьдач нөхцөл **1**.

| ID | Сонголтуудын хослол | Оюутан (setup) | Хичээл (setup) | Хүлээгдэх статус | Хүлээгдэх `result` |
|---|---|---|---|---|---|
| **S1** | F1a · F2a · F3a · F4b | `active`, `coursesTaken=[CS201]` | `CS313`, `prerequisites=[CS201]` | **201** | `OK` |
| **S2** | F1b · F2a · F3a · F4b | `inactive`, `coursesTaken=[CS201]` | `CS313`, `prerequisites=[CS201]` | **200** | `ERROR_INACTIVE_STUDENT` |
| **S3** | F1c · F3a · F4b | _(бүртгэлгүй)_ | `CS313`, `prerequisites=[CS201]` | **200** | `ERROR_NO_STUDENT` |
| **S4** | F1a · F3b | `active`, `coursesTaken=[CS201]` | _(бүртгэлгүй)_ | **200** | `ERROR_NO_COURSE` |
| **S5** | F1a · F2b · F4c | `active`, `coursesTaken=[CS101]` (холбоогүй) | `CS313`, `prerequisites=[CS201]` | **200** | `ERROR_PREREQUISITES` (`missing=["CS201"]`) |
| **S6** | F1a · F4a — _хязгаар_ | `active`, `coursesTaken=[]` | `CS101`, `prerequisites=[]` | **201** | `OK` |
| **S7** | F1a · F2b — _хязгаар: хоосон `coursesTaken`_ | `active`, `coursesTaken=[]` | `CS313`, `prerequisites=[CS201]` | **200** | `ERROR_PREREQUISITES` (`missing=["CS201"]`) |
| **S8** | F5b — _хязгаар: талбар дутуу_ | `active`, `coursesTaken=[CS201]` | `CS313`, `prerequisites=[CS201]` | **400** | `ERROR_BAD_REQUEST` |
| **S9** | F1b · F3b — _давхар алдаа_ | `inactive`, `coursesTaken=[]` | _(бүртгэлгүй)_ | **200** | `ERROR_INACTIVE_STUDENT` |
| **S10** | F1c · F4b — _давхар алдаа_ | _(бүртгэлгүй)_ | `CS313`, `prerequisites=[CS201]` | **200** | `ERROR_NO_STUDENT` |
| **S11** | F1a · F2c · F4d — _зарим нь_ | `active`, `coursesTaken=[CS201]` | `CS313`, `prerequisites=[CS201,CS202]` | **200** | `ERROR_PREREQUISITES` (`missing=["CS202"]`) |
| **S12** | F6b — _хязгаар: эвдэрсэн JSON_ | _(шаардлагагүй)_ | _(шаардлагагүй)_ | **400** | `ERROR_BAD_JSON` |
| **S13** | F5b — _хязгаар: хоосон мөр_ | `studentID=""` | `CS313`, `prerequisites=[]` | **400** | `ERROR_BAD_REQUEST` |

**Тайлбар — S9 ба S10 (давхар алдаа).** Зааварт аль алдаа түрүүлж буцахыг заагаагүй тул
үүнийг тестээр тогтоосон: сервер **эхлээд оюутанг** шалгадаг. S9-д оюутан идэвхгүй,
хичээл байхгүй — гэвч `ERROR_INACTIVE_STUDENT` буцна. S10-д оюутан байхгүй, урьдач
нөхцөл дутуу — гэвч `ERROR_NO_STUDENT` буцна. Хэрэв сервер хичээлээ түрүүлж шалгасан бол
S9 → `ERROR_NO_COURSE`, S10 → `ERROR_PREREQUISITES` байх байсан.

## 4. Тестийн багц — `lab05-collection.json`

Collection нь **14 хавтас**тай: 13 спецификаци (S1–S13) + 1 нэмэлт нийтийн API хавтас.
Хавтас бүр өөрийн setup `PUT` хүсэлтүүдийг агуулна — тестүүд **бие даасан** (Лекц 4-ийн
test independence). Тест бүрд өөрийн `studentID` оноосон тул "оюутан байхгүй" гэх мэт
тохиолдлууд бусад тестийн үлдээсэн төлөвөөс хамаарахгүй.

| Хавтас | Спецификаци | Oracle-ууд |
|---|---|---|
| 01 | S1 happy path | статус 201 · `result="OK"` · `registrationID` эерэг тоо |
| 02 | S2 идэвхгүй оюутан | статус 200 · `result` |
| 03 | S3 бүртгэлгүй оюутан | статус 200 · `result` |
| 04 | S4 байхгүй хичээл | статус 200 · `result` |
| 05 | S5 урьдач нөхцөл огт үзээгүй | статус 200 · `result` · `missing=["CS201"]` |
| 06 | S6 урьдач нөхцөлгүй хичээл | статус 201 · `result="OK"` · `registrationID` |
| 07 | S7 хоосон `coursesTaken` | статус 200 · `result` · `missing=["CS201"]` |
| 08 | S8 талбар дутуу | статус 400 · `result` |
| 09 | S9 давхар алдаа (идэвхгүй + байхгүй) | статус 200 · `result` |
| 10 | S10 давхар алдаа (байхгүй + урьдач) | статус 200 · `result` |
| 11 | S11 зарим урьдач нөхцөл | статус 200 · `result` · `missing=["CS202"]` |
| 12 | S12 эвдэрсэн JSON | статус 400 · `result` |
| 13 | S13 хоосон мөр | статус 400 · `result` |
| 14 | _(нэмэлт)_ нийтийн API | статус 200 · массив эсэх · эхний хэрэглэгчийн нэр |

**`registrationID`-ийн яг утгыг шалгаагүй** — сервер in-memory тул ажиллуулах бүрд
хуримтлагддаг. Зөвхөн "тоо байгаа ба 0-ээс их" гэдгийг шалгасан.

**Нийт oracle: 34** — энэ тоо `results/newman-pass.txt` дахь **`assertions executed = 34`**-тэй
яг таарна (13 спецификаци хавтас тус бүр 2–3 oracle = 31, нийтийн API хавтас 3 oracle).

## 5. Newman ажиллуулалт

```bash
mkdir -p results

# PASS — үндсэн collection
newman run lab05-collection.json 2>&1 | tee results/newman-pass.txt
echo "exit=${pipestatus[1]}"

# FAIL — зориуд буруу oracle-той collection
newman run lab05-collection-fail.json 2>&1 | tee results/newman-fail.txt
echo "exit=${pipestatus[1]}"

# DOWN — сервер унтарсан үед
newman run lab05-collection.json 2>&1 | tee results/newman-down.txt
echo "exit=${pipestatus[1]}"
```

| Ажиллуулалт | iterations | requests | test-scripts | assertions | Exit code |
|---|---|---|---|---|---|
| **PASS** (`newman-pass.txt`) | 1 | 33 / 0 failed | 14 / 0 failed | **34 / 0 failed** | **0** |
| **FAIL** (`newman-fail.txt`) | 1 | 33 / 0 failed | 14 / 0 failed | **34 / 1 failed** | **1** |
| **DOWN** (`newman-down.txt`) | 1 | 33 / **32 failed** | 14 / 0 failed | **34 / 31 failed** | **1** |

### PASS — ногоон

33 хүсэлт бүгд амжилттай, 34 oracle бүгд PASS. `exit code 0` — CI quality gate нээгдэнэ.

### FAIL — зориуд улаан

`lab05-collection-fail.json` нь үндсэн collection-той ижил, гэхдээ **тест 01-ийн статус
oracle-ыг зориуд буруу** болгосон: `201`-ийн оронд `200` хүлээж байна. Үр дүн:

```
1.  AssertionError  Status code is 200 OK
                    expected response to have status code 200 but got 201
```

`assertions failed = 1`, `exit code 1` — CI дээр энэ нь build-ыг унагаана.
Үндсэн `lab05-collection.json` зөв хэвээр үлдсэн.

### DOWN — интерфейсийн алдаа

Серверийг `Ctrl+C`-ээр унтраагаад дахин ажиллуулахад 33 хүсэлтийн 32 нь

```
connect ECONNREFUSED 127.0.0.1:3000
```

алдаатай унасан (`exit code 1`). **Энэ нь интерфейсийн (холболтын) алдаа, oracle-ийн алдаа
биш** — хүсэлт серверт хүрэлгүй байгаа тул шалгах хариу огт байхгүй. Харин FAIL тохиолдолд
хүсэлт серверт хүрч, хариу ирсэн ч oracle буруу хүлээж байсан — өөрөөр хэлбэл код ажиллаж
байгаа, тестийн хүлээлт буруу байсан. Энэ хоёрыг ялгах нь чухал: интерфейсийн алдаа нь
"тестийн орчин бэлэн биш", oracle-ийн алдаа нь "тестийн хүлээлт буруу".

_(DOWN ажиллуулалтад 34 oracle-ын 3 нь PASS хэвээр байсан — тэдгээр нь 14-р хавтасны
интернетаар ажилладаг нийтийн API-ийн oracle-ууд юм.)_

## 6. Дүгнэлт

Таван алхмын дунд хамгийн их бодол шаардсан нь **Алхам 3 — спецификаци сонгох** байлаа,
учир нь 6 факторын бүх хослолын тоо зуугаас давдаг ч дийлэнх нь ижил зан төлөв үзүүлдэг
тул тэдгээрийг эквивалент ангид нэгтгэж, ердөө 13 спецификаци үлдээх шийдвэр гаргах
шаардлагатай болсон. Хоёр дахь хүнд алхам нь **Алхам 1** байсан — сервер in-memory учир
тестүүд нэг нэгнийхээ төлөвийг бохирдуулах эрсдэлтэй байв; үүнийг тест бүрд өөрийн
`studentID` (B0000000NN) оноож, өөрийн setup `PUT`-уудыг хийлгэснээр шийдсэн.
**Боломжгүй хослол** гэж `ERROR_NO_COURSE` ба `ERROR_PREREQUISITES`-ийг хамт авахыг
бодож үзсэн — хичээл байхгүй бол урьдач нөхцөлийг шалгах боломжгүй тул ийм хослол
оршин байхгүй. Үүнтэй адил S9, S10 нь "аль алдаа түрүүлэх вэ" гэдгээр тодорхойлогдох
хослолууд бөгөөд сервер **эхлээд оюутанг, дараа нь хичээлийг** шалгадаг нь тестээр
батлагдсан (зааварт энэ дарааллыг заагаагүй байсан). Тестүүд **согог олоогүй** — бүх
34 oracle PASS болж `exit code 0` гарсан нь сервер өөрийн спецификацид нийцэж ажиллаж
байгааг харуулна. Гэвч тестийн явц нэг бодит орчны асуудлыг илрүүлсэн: системийн
`HTTP_PROXY` тохиргооноос болж Newman локал хүсэлтүүдийг proxy-гоор дамжуулж, эхний
ажиллуулалтад бүх тест `404 ERROR_NOT_FOUND` буцааж байсан — энэ нь oracle-ийн бус,
**тестийн орчны алдаа** байсан бөгөөд `NO_PROXY=localhost,127.0.0.1` тавьснаар
шийдэгдсэн. Ерөнхий сургамж нь: CI-д Newman ажиллуулахдаа орчны хувьсагчдыг хянахгүй
бол "код зөв, гэхдээ тест улаан" гэсэн төөрөгдөл үүсдэг.

## 7. Нэмэлт даалгавар — AI өнцөг

Лекц 5-ын процессын дагуу `server.js`-ийг **тусдаа AI туслахад** өгч, дараах prompt бичсэн:
_"Энэ API-гийн POST /registrations функцийн сонголтуудыг тодорхойлж, сонголт бүрийг
эквивалент ангид хуваагаад, ангиудын хослолоор Postman тестүүд үүсгэ."_ AI 12 спецификаци
гаргасан ба түүний дийлэнх нь миний дизайнтай давхцсан. **(1) AI миний мартсан 2 зүйлийг
олсон**: эвдэрсэн JSON → `400 ERROR_BAD_JSON`, мөн хоосон мөр (`studentID=""`) →
`400 ERROR_BAD_REQUEST`; эдгээрийг S12, S13 болгож collection-д нэмсэн. **(2)** Харин
миний дизайнд байсан "огт хангагдаагүй" анги (холбоогүй хичээл үзсэн — S5, эсвэл хоосон
`coursesTaken` — S7) AI-ийн жагсаалтад тусдаа спецификаци болж ороогүй, тэр хоёрыг
нэгтгэж үзсэн; AI-ийн `coursesTaken` нь `prerequisites`-тай яг тэнцүү гэсэн нэг
спецификаци миний S1-тэй давхцаж байсан тул тусдаа утга нэмээгүй. **(3) AI-ийн oracle-ууд
бүгд зөв** байсан — ялангуяа давхар алдааны үед S9 → `ERROR_NO_STUDENT`,
S10 → `ERROR_INACTIVE_STUDENT` гэж шалгалтын дарааллыг зөв таамагласан нь серверийн
кодыг зөв уншсаныг харуулна. AI мөн нэмэлт oracle санал болгосон (`GET /registrations`
өсөөгүй эсэх) — сайн санаа боловч энэ collection-д ороогүй.
